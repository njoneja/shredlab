# app/src-tauri

The Tauri 2 shell of ShredLab (cargo package `shredlab`, library
`shredlab_lib`): the commands and events the UI uses, the state of the open
song, the background jobs (separation, beats, export, separation strength),
app settings and model discovery. The audio, DSP, separation and library work
itself lives in the crates under [crates/](../../crates).

## Boundaries

- Owns: the command and event contract, which is specified in
  [app/src/lib/API.md](../src/lib/API.md) (the backend implements exactly
  that), the single open song and its in-memory stems, job lifetimes and
  cancellation, `settings.json`, where models and data live, logging, and
  the bundle configuration.
- `src/backend.rs` is Tauri-free. Events leave through a `Sink` closure
  (`(name, JSON payload)`), and paths come in through `Config`, so the same
  code runs in the app, in the debug autotest and in unit tests (which pass a
  recording sink and no audio engine). Only `src/lib.rs`, `src/commands.rs`,
  `src/autotest.rs` and `src/win_icon.rs` touch Tauri.
- Does not decide UI policy: the UI picks which stems are audible for an
  export, computes the effective downbeats from meter overrides, and decides
  when to re-separate after a settings change. Per-song UI settings
  (`save_song_settings`) are stored verbatim and never interpreted.
- Depends on the six `shredlab-*` library crates (none depend on Tauri).
  Its only user is the UI in [app/src](../src), via `app/src/lib/api.tauri.ts`.

## Layout

Start with `src/lib.rs` (setup and the command list), then `src/commands.rs`,
then `src/backend.rs`.

- `src/main.rs`: calls `shredlab_lib::run()`; hides the console in release builds.
- `src/lib.rs`: `run()` registers the dialog plugin and every command;
  `setup` picks the data dir, opens the log, fits and shows the window, builds
  `Config`, creates the audio engine (optional) and the `Backend`, wires the
  event sink to `AppHandle::emit`, and starts the debug autotest. On
  `RunEvent::Exit` it flushes the pending song save. Also the
  one-time move of the data folder from the pre-rename identifier
  `dev.stemextractor.app`.
- `src/commands.rs`: `#[tauri::command]` wrappers, all `async`; slow ones go
  through `spawn_blocking`. The native file dialogs are opened here.
- `src/backend.rs`: `Backend` with all state and jobs, plus the pure helpers
  the tests cover (audibility and gains, choosing the original-based mix
  mode, downbeat snapping, waveform peaks, progress throttling).
- `src/types.rs`: serde types of the contract, field names exactly as the JSON.
- `src/settings.rs`: `AppSettings` (`<data dir>/settings.json`), `Quality`, `StemFormat`, theme names.
- `src/models.rs`: separation model search dirs, beat model lookup, default model choice.
- `src/music_start.rs`: detects where the music starts after a quiet intro (pure function of the mix and the beats).
- `src/audio.rs` re-exports `shredlab-audio`; `src/log.rs` is the `log!` macro (stderr and `<data dir>/shredlab.log`).
- `src/autotest.rs`: debug-only headless end-to-end check.
- `src/win_icon.rs`: Windows only; sharper window and taskbar icons.
- `build.rs`: runs `tauri_build` and stamps the short commit hash (`SHREDLAB_COMMIT`, empty outside git) into the startup log line.
- `tauri.conf.json`: window, CSP, bundle resources and icons.
  `tauri.bundle.windows.conf.json` adds `DirectML.dll` for installers (see Build below).
- `capabilities/default.json`: permissions of the main window (`core:default` only).
- `icons/`: generated from `icons/app-icon.svg`; `gen/` is generated by Tauri and gitignored.

## How it works

**State.** One `Mutex<State>` holds the open song (`Song`: the original mix
at 44.1 kHz as f32, the original as a track sharing those samples, the
loaded stems as 16-bit integers (`Track::quantized`, half the memory of f32)
and which cached set they are, beats, music start, the strength they were derived with), the
transport settings the UI last sent (mix, speed, pitch, loop, click,
effective downbeats), the running jobs, Refine settings and the stem under
stereo-field analysis. Transport settings survive a song switch; `open_song`
resets the loop and downbeats and re-applies everything to the engine.
`generation` is bumped on every open and close; a background result is
applied only if its generation and song id are still current.

**Commands.** Every command is `async`, so none runs on the main thread.
Anything that decodes, reads stems, walks the library, writes settings or
opens a dialog runs in `spawn_blocking` (the `blocking` helper). Long work
returns at once and reports through events. `open_song` and `delete_song`
are serialized by `open_lock`.

**Background threads** (named `shredlab-*`, started by `spawn`):

| Thread | Started by | Cancellation |
|---|---|---|
| separation | `start_separation` | `AtomicBool`, set by `cancel_separation`, `open_song`, `close_song` |
| beats | `open_song` when the grid isn't cached | none; the result is saved to `song.json` regardless and applied only if still current |
| export | `export_mix` | `AtomicBool`, set by `cancel_export`; the partial file is deleted |
| strength | `set_strength`, `open_song`, a finished separation | `AtomicBool`; a newer job, `open_song` or `close_song` cancels the older one |
| position | `start_background` | runs for the life of the backend |
| preload | `start_background` | loads the current model once (skipped with `SHREDLAB_NO_PRELOAD`) |

The canceler, not the job, emits the `*-error` event with `canceled: true`
for separation and export; a job that sees its flag just returns. A
separation whose (model, quality) set is already cached reads it from disk
instead, with the same events. The loaded `Separator` is kept between runs
and replaced only when the model changes; if a GPU run fails over to CPU,
`device_label` follows. Strength never writes stems: it re-reads the cached
set, re-derives it from the original (`shredlab-dsp` `strength`) and swaps
it in memory. Strength job ids increase monotonically; `open_song` returns
the id of the job it started in `SongInfo.strength_job`.

**Position thread.** Every 33 ms it flushes a pending song save (Refine and
per-song settings, 600 ms after the last `set_refine` or
`save_song_settings` for the open song; this part runs without an audio
engine too), emits `refine-field` for the analyzed stem
when the engine has new data, and emits `playback-position` while playing
or counting in, plus once when that stops. Play, pause, seek, `open_song`,
end of song and loop wraps emit a position immediately (the engine calls
back through weak references to the backend).

**Model discovery** (`src/models.rs`). Separation models are scanned, in
order, from `<resource dir>/models` (bundled), `<data dir>/models`
(personal), each `SHREDLAB_MODELS_DIR` entry, and in debug builds the repo's
`models/registry` and `models/personal`. The first folder with a given id
wins; later duplicates are logged as problems. The model used is
`SHREDLAB_MODEL` if installed, else the saved choice, else `htdemucs_6s`,
else the first non-personal model. The beat model file
`beat_this_final0.onnx` is looked up at `SHREDLAB_BEAT_MODEL` (a file
path), then in the same places (debug: `models/onnx/`). Without it beats
are skipped and the click falls back to defaults.

**Device and quality.** Separation uses `SHREDLAB_DEVICE` (default `auto`),
beats `SHREDLAB_BEATS_DEVICE` (default `cpu`; that model has no self-test;
a GPU failure retries on CPU). Before a model is loaded, `predict_device`
guesses the label from the loaded separator or the cached self-test result;
the default quality is High for "GPU", Standard for "CPU".

**Settings.** `AppSettings` stores only what the user chose; `None` means
the default and is resolved on read (`theme()`, `click_volume()`, ...).
Each setter validates, then goes through `update_settings`, which holds
the `app_settings` lock while it changes a copy, writes the whole file
atomically (temp file and rename) and stores the copy, so concurrent
setters cannot lose each other's change; the engine is updated after the
lock is released. A missing or corrupt file gives defaults; unknown fields are
ignored. Master volume is applied at startup; the click volume seeds
`ClickState`.

**Data dir.** `SHREDLAB_DATA_DIR`, else the Tauri app data dir (on
Windows `%APPDATA%\io.github.njoneja.shredlab`). It holds `library/`
(`shredlab-library`), `cache/` (self-test and checksum cache),
`models/` (personal models), `settings.json` and `shredlab.log` (rotated to
`shredlab.old.log` above 5 MB).

**Build and bundle.** `tauri.conf.json` runs `pnpm dev` / `pnpm build` in
`app/` and embeds `app/dist` into the binary. Bundle resources are the
`htdemucs_6s` registry folder and the beat model (from the gitignored
`models/` folder at the repo root) and `app/public/THIRD_PARTY_LICENSES.html`.
The window starts hidden and `setup` shows it after shrinking it to the
monitor's work area. Installers come from `app/scripts/bundle.mjs`
(`pnpm build-installers` at the root), which regenerates the license file,
builds the frontend and the release exe, stages a real copy of
`DirectML.dll` in `target/bundle-res`, then runs `tauri build` with
`tauri.bundle.windows.conf.json` on Windows only. The crate is `rlib` only,
so no DLL of the app itself lands in the installers. Icons are made with
`tools/make_icon.py` and `pnpm --dir app tauri icon src-tauri/icons/app-icon.svg`.

## Invariants and gotchas

- The contract has five copies that must agree: `src/commands.rs` and
  `src/types.rs`, [API.md](../src/lib/API.md), and on the UI side
  `app/src/lib/types.ts`, `api.tauri.ts` and `api.mock.ts`. TypeScript checks
  the last three against each other; nothing checks Rust against TypeScript.
- No `rename_all` on commands or types: JS camelCase argument keys map to
  snake_case parameters by Tauri's default, and struct fields stay
  snake_case in JSON. A new command must also be added to
  `generate_handler!` in `src/lib.rs`, or `invoke` fails at run time.
- Never write a synchronous `#[tauri::command]`: it would run on the main
  thread and freeze the window. The dialogs use the plugin's blocking API,
  which must stay inside `spawn_blocking`.
- `predict_device` uses `try_lock` on the separator because a separation
  (and the startup preload) holds that lock for the whole run. Don't lock
  `separator` or `beat_model` from a command path.
- Lock order is `st` then `app_settings` (`click_config` takes the second
  while holding the first). Never take `st` while holding `app_settings`.
  Jobs drop `st` before emitting events.
- Check `generation` (and the song id) before applying any background
  result; the UI separately ignores events for a song that isn't current.
- `play`, `pause`, `seek` and `set_*` must not fail without a song. `play`
  is the one transport command that returns `Err`: when a song is open but
  there is no audio output device (the engine is optional; separation and
  export still work).
- `delete_song` refuses the open song, and both it and `song_size` go
  through `shredlab-library`'s id checks; don't build song paths here.
- Capabilities: the UI only needs `core:default` (events and drag-drop),
  because dialogs are opened from Rust. A frontend plugin API would need its
  permission added to `capabilities/default.json`. Keep `dragDropEnabled` at
  its default.
- The CSP blocks inline scripts and `data:` fonts: hence
  `app/public/theme-init.js` as a file and Vite's no-inline rule for `.woff2`.
- Theme names are duplicated in `settings::THEMES`, `app/src/lib/types.ts`,
  `app/public/theme-init.js`, `app/index.html` and `app/src/app.css`.
- `tauri.windows.conf.json` would be merged into every build, including
  `tauri dev` and `cargo test`, before the release `DirectML.dll` exists;
  that is why the Windows bundle config is passed explicitly by `bundle.mjs`.
- Refine and per-song settings of the open song live in `State` until the
  debounced save; anything that switches or closes the song, or ends the
  app, must call `flush_song_save(true)` first (`open_song`, `close_song`
  and the exit hook in `src/lib.rs` do). A hard kill loses the last 600 ms.

## Testing

From the repo root (these build `app/dist` first, which the crate embeds;
the build also needs the bundled model files from
`python tools/setup_models.py`, because they are bundle resources):

```sh
pnpm test                     # cargo test --workspace
pnpm check                    # includes clippy -D warnings on this package
cargo test -p shredlab        # this package only, once app/dist exists
```

The unit tests need no models or audio device: they build a `Backend` on a
temp data dir with a recording sink and generated WAVs. One ignored test
runs music-start detection on real songs:
`SHREDLAB_MUSIC_START_SONGS="a.mp3;b.mp3" cargo test -p shredlab --lib music_start::tests::real_songs -- --ignored --nocapture`.

Headless end-to-end check (debug builds; needs the models and an audio
device):

```sh
SHREDLAB_AUTOTEST=<song> SHREDLAB_AUTOTEST_EXIT=1 pnpm dev
```

The steps are listed at the top of `src/autotest.rs`; exports are checked
numerically, saved settings are restored, and the last line is
`AUTOTEST PASS` or `AUTOTEST FAIL: ...` (exit code 0 or 1 with `_EXIT`).
Exports go to `<data dir>/autotest` or `SHREDLAB_AUTOTEST_OUT`. Use a fresh
`SHREDLAB_DATA_DIR` to time separations from scratch. Other environment
variables are in [docs/DEVELOPING.md](../../docs/DEVELOPING.md).

## Common changes

- **New command:** add the method on `Backend` (Tauri-free, `Result<T,
  String>` with a user-readable message), types in `src/types.rs`, the
  `async` wrapper in `src/commands.rs` (through `blocking` if it does I/O or
  waits on a lock a job may hold), register it in `src/lib.rs`, document it
  in API.md, then add it to `Backend` in `app/src/lib/types.ts`, to
  `api.tauri.ts` and `api.mock.ts`, and call it from `app/src/lib/store.svelte.ts`.
- **New app setting:** an `Option<T>` field in `AppSettings` with
  `#[serde(default, skip_serializing_if = "Option::is_none")]` and a getter
  that resolves the default; a field in `AppSettingsInfo`; a `Backend`
  setter that changes it through `update_settings`; a command returning
  `AppSettingsInfo`; extend `persistence_roundtrip`; then API.md and the UI
  side as above.
- **New event:** a payload struct in `src/types.rs`, `self.emit(name, &payload)`
  from the backend (throttle progress to 10 Hz with `Throttle`), a row in
  API.md, an entry in `EventMap` in `app/src/lib/types.ts`, a listener in
  `AppState.init()`, and a mock emitter. Add high-rate events to the
  autotest's filter in `event_tap`.
- **New background job:** follow the export or strength job: store an
  `Arc<AtomicBool>` in `State`, capture `generation`, spawn with `spawn`,
  clear the job record only if it is still yours (`Arc::ptr_eq` or the job
  id), and cancel it in `open_song`/`close_song` if it belongs to the song.
